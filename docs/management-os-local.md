# Management OS v0 в Staff CRM

Локальный раздел `/management` использует существующие справочники сотрудников и команд. Производственный облачный режим остаётся доступен прежними командами; Management OS в нём пока не включена.

## Запуск

Двойной щелчок по `Запустить локально.command` в корне проекта. Либо из `app`:

```sh
npm run build:local
npm run start:local -- --open /management
```

Адрес: http://127.0.0.1:4310/management. Остановка: Ctrl+C в окне запуска. Для разработки: `npm run dev:local`.

`VITE_LOCAL_MODE=true` выбирается при сборке и запуске. В этом режиме Supabase-клиент не создаётся, авторизация локальная, записи стандартных репозиториев идут в сервер на этом ПК. Не используйте облачную сборку `dist` вместо локальной `dist-local`. Публичное размещение, миграции Supabase и деплой не выполнялись.

## Данные

- Единственный постоянный источник — `app/.local-data/staff-crm.json` (CRM + Management OS).
- Последние 30 предыдущих версий — `app/.local-data/backups/`.
- Файлы создаются с доступом владельцу; каталог исключён из Git.
- Кэш и очередь локального режима имеют префикс `crm-local`, отдельно от облачных ключей.
- В разделе «Управление → Данные» или «Настройки» доступны полная JSON-копия и восстановление с подтверждением.
- Восстановление проверяет формат и версии; перезапись при изменениях в другой вкладке отклоняется. Копия содержит персональные данные.
- Management OS использует контроль версии при каждом сохранении. Старый CRM-слой сохраняет существующую модель очереди; редактуру одной CRM-карточки одновременно в нескольких вкладках лучше не выполнять.
- Существующие облачные записи не скачиваются автоматически. Сотрудников и команды можно перенести через существующий предпросмотр импорта JSON в «Настройках». Это создаёт локальный рабочий набор; последующая синхронизация с облаком отключена.

## Первый запуск

1. Импортировать или завести команды и сотрудников в CRM.
2. В «Рабочий стол → Ритм и редкие проверки → Ритм» сопоставить команды границам ответственности: ЕФС / City+ / Знание о клиенте — Delivery + People; Платёжные инструменты — только Delivery; Пассивы ЕФС — только People. Не создаётся второй справочник команд.
3. Указать начало спринта и фактические квартальные даты.
4. Заполнять реальные действия, проблемы и оценки по мере появления. Никаких стартовых задач и фиктивных Green-оценок нет.

## Источники истины

- Реестр хранит управленческие действия; Backlog — системные проблемы. Связь действия с исходной записью не копирует её статус.
- Рабочий стол хранит только ссылки общего фокуса (развитие TODAY), включая задачи CRM, ИПР и встречи. Сроки и отклонения вычисляются из источников. Выбор не переносится на следующий день.
- Разовые действия по теме дня хранятся в Rhythm. При переносе в Реестр исходная запись получает ссылку на действие; повторное независимое редактирование исключено.
- Карточки команды / сотрудника и календарь читают те же записи Management OS.
- Существующие задачи сотрудников, личные списки и action items из feedback не импортируются массово в Реестр и не считаются обязательствами руководителя автоматически. Не создавайте параллельные копии одного обязательства в двух списках; эта версия не выполняет автоматическую миграцию старых задач.
- Pulse, рассчитанный риск ухода и прогноз capacity CRM остаются прежними инструментами. Они не подменяют ручные сигналы DPO и не создают исключений / задач автоматически.

## Проверки и переходы

CONTROL и MONITORING с наступившей датой видны как требующие решения. Портал не подменяет решение пользователя автоматическим статусом: редактирование такого объекта требует DONE / OPEN или CLOSED / IN WORK соответственно. Другие действия доступны, пока ожидается решение.

WAITING имеет дату следующего контроля в существующем поле срока. Если ожидаемое событие случилось раньше, вручную вернуть действие в OPEN. Отдельный автоматический источник событий не вводится.

Квартальная readiness не становится шестым сигналом Scorecard. People и Planning/Improvement ограничиваются ответственностью команды. В Accountability нет скоринга, подсчёта частоты и сортировки сотрудников по числу наблюдений.

## Спецификация

Эталон сохранён без изменений в `app/src/ui/screens/management/Management_OS_v0.md` и доступен в разделе «Спецификация». Веб-реализация расширяет первоначальное ограничение «без автоматизации» только на отображение, работу с датами и локальное сохранение. Управленческие решения и ввод данных остаются ручными.

## Проверка

```sh
npm run typecheck
npm test
npm run lint
npm run build:local
```

Новые проверки покрывают фильтры Cockpit, границы недель, применимость сигналов, переходы, тест системности, смену дня, ссылочную целостность, локальное сохранение, перезапуск, конфликт версий и резервные копии. Браузерная проверка выполняется с отдельным временным каталогом `CRM_LOCAL_DATA_DIR`, чтобы тестовые данные не попадали в рабочий файл.

Текущая архитектура рабочего стола и общего ритма: [management-crm-rhythm.md](management-crm-rhythm.md).
